Der Authentifizierungsdienst prüft Identitäten und unterstützt je nach Workspace-Konfiguration Passwort, Einmalcode (OTP), Google, Microsoft, Azure AD, OAuth und SAML SSO. Novaplan richtet die zugelassenen Methoden für den Kunden-Workspace ein. Diese Seite fasst die technischen Abläufe zusammen; sie ersetzt keine Freigabe zur direkten Nutzung interner Endpunkte.

<Warning>
  Diese aus dem Quelltext abgeleitete Referenz ist kein geprüfter Vertrag für die bereitgestellte Novaplan-Enterprise-API. Administrative und interne Endpunkte sind keine allgemeinen Kundenschnittstellen. Prüfen Sie Routen, Felder, Scopes und aktivierte Anmeldemethoden mit Novaplan, bevor Sie die Beispiele automatisieren. Für Kundenintegrationen gilt die [OAuth-Anwendungsanleitung](/de/developer/oauth2).
</Warning>

## Mehrstufige Anmeldung

1. Der Client sendet die E-Mail-Adresse an `POST /api/v1/userAccount/initAuth`.
2. Der Dienst erzeugt eine temporäre Sitzung und gibt ein `x-session-token` sowie die verfügbaren Anmeldemethoden zurück.
3. Der Client sendet die gewählte Methode und die benötigten Daten an `POST /api/v1/userAccount/authenticate` und übergibt dabei `x-session-token`.
4. Wenn ein weiterer Faktor verlangt wird, wiederholt der Client den Anmeldeschritt mit den angeforderten Daten. Nach erfolgreicher Anmeldung erhält er ein Access Token und ein Refresh Token.

Temporäre Sitzungen werden in Redis über eine eindeutige Kennung verwaltet und nach Abschluss oder Ablauf gelöscht. Die technische Referenz nennt dafür standardmäßig **eine Stunde**. Sie nennt für das Access Token typischerweise **eine Stunde** und für das Refresh Token typischerweise **sieben Tage**; die tatsächlichen Laufzeiten und Methoden müssen für die bereitgestellte Novaplan-Version geprüft werden. Das Access Token enthält die Identität und Berechtigungen der angemeldeten Person und dient ihren API-Anfragen. Das Refresh Token erneuert den Zugriff ohne erneute vollständige Anmeldung.

`x-session-token` kommt bei `initAuth` im **Response-Header**, nicht im JSON-Body zurück. Bewahren Sie es nur für den laufenden Anmeldevorgang auf und senden Sie es bei jedem folgenden Aufruf von `authenticate` als Request-Header mit.

### Anmelde-Requests und Antworten

`initAuth` erwartet einen Body mit `email`. Eine erfolgreiche Antwort kann `currentStep`, `allowedMethods` und Angaben zu den verfügbaren Anbietern enthalten:

```json
{
  "email": "user@example.com"
}
```

`authenticate` erwartet `method` und `credentials`. Die dokumentierten Methoden sind `password`, `otp`, `google`, `microsoft`, `azureAd`, `oauth` und `samlSso`. Für Passwort verwenden die `credentials` ein Feld `password`, für Einmalcode ein Feld `otp`. Bei Google ist ein ID-Token dokumentiert; Microsoft, Azure AD und generisches OAuth verwenden Access- und ID-Token des jeweiligen Identitätsanbieters. Senden Sie nur die Felder, die der aktuelle Anmeldeschritt verlangt.

Wenn weitere Schritte nötig sind, kann die Antwort `nextStep` und die nächsten `allowedMethods` enthalten. Nach Abschluss liefert sie `accessToken` und `refreshToken`; die temporäre Redis-Sitzung wird beendet. Behandeln Sie alle Tokens als vertrauliche Werte.

## Datenmodelle und Organisationsregeln

| Modell | Technische Felder und Aufgabe |
| --- | --- |
| `OrgAuthConfig` | Organisations-ID, optionale Domain und geordnete `authSteps` mit erlaubten Methoden. |
| `UserCredentials` | Benutzer- und Organisationszuordnung, IP-Adresse, gehashte Passwörter und Einmalcodes, Zähler fehlgeschlagener Versuche sowie Sperrstatus. |
| `UserActivities` | Ereignisse wie `LOGIN`, `LOGOUT`, `LOGIN_ATTEMPT`, `OTP_GENERATE`, `WRONG_OTP`, `WRONG_PASSWORD` und `REFRESH_TOKEN`. |
| `SessionData` | Benutzer, E-Mail, Organisation, Authentifizierungsschritte, aktueller Schritt und temporärer Zustand der Anmeldung. |

Eine Organisationskonfiguration kann laut Referenz **ein bis drei** Authentifizierungsschritte enthalten. Jeder Schritt braucht eine eindeutige Reihenfolge und mindestens eine Methode. Dieselbe Methode darf weder innerhalb eines Schritts noch in verschiedenen Schritten doppelt vorkommen. Änderungen an diesen Regeln können bestehende Anmeldungen unterbrechen; sie gehören in einen geprüften Administrationsablauf.

## Endpunkte

Die technische Referenz nennt folgende Pfade. Die meisten geschützten Aufrufe erwarten `Authorization: Bearer <token>`; interne Service-Aufrufe können eigene Scopes wie `PASSWORD_RESET`, `TOKEN_REFRESH` oder `FETCH_CONFIG` verlangen.

| Methode und Pfad | Aufgabe |
| --- | --- |
| `POST /api/v1/userAccount/initAuth` | Anmeldung beginnen und mögliche Methoden ermitteln |
| `POST /api/v1/userAccount/authenticate` | Einen Anmeldeschritt abschließen |
| `POST /api/v1/userAccount/login/otp/generate` | Einmalcode anfordern |
| `POST /api/v1/userAccount/oauth/exchange` | OAuth-Daten austauschen |
| `POST /api/v1/userAccount/password/forgot` | Passwortzurücksetzung anstoßen |
| `POST /api/v1/userAccount/password/reset/token` | Passwort mit einem Zurücksetzungstoken ändern |
| `POST /api/v1/userAccount/password/reset` | Passwort zurücksetzen |
| `POST /api/v1/userAccount/refresh/token` | Access Token erneuern |
| `POST /api/v1/userAccount/logout/manual` | Sitzung beenden |
| `GET /api/v1/saml/signIn` | SAML-Anmeldung beginnen |
| `POST /api/v1/saml/signIn/callback` | SAML-Antwort verarbeiten |
| `POST /api/v1/saml/updateAppConfig` | SAML-Konfiguration administrativ ändern |
| `GET /api/v1/orgAuthConfig/authMethods` | Erlaubte Anmeldemethoden abrufen |
| `POST /api/v1/orgAuthConfig/updateAuthMethod` | Anmeldemethoden administrativ ändern |
| `POST /api/v1/orgAuthConfig/` | Organisationskonfiguration anlegen |
| `GET /api/v1/userAccount/internal/password/check` | Intern prüfen, ob Passwortanmeldung aktiviert ist |

<Warning>
  Endpunkte für SAML-Konfiguration, Organisationsauthentifizierung und interne Prüfungen sind nicht für gewöhnliche Kundenanwendungen bestimmt. Stimmen Sie deren Nutzung mit Novaplan ab. Tokens, Einmalcodes und Zurücksetzungslinks dürfen nicht protokolliert oder in Chats geteilt werden.
</Warning>

## Antworten nach Funktionsbereich

- **Einmalcode:** `POST /userAccount/login/otp/generate` erzeugt für die aktuelle Anmeldesitzung einen einmalig gültigen Code. Der nachfolgende `authenticate`-Schritt übergibt ihn in `credentials.otp`.
- **OAuth:** `POST /userAccount/oauth/exchange` tauscht die Daten eines zugelassenen OAuth-Anbieters gegen die für den Novaplan-Anmeldeablauf benötigten Angaben aus. Für Kundenintegrationen gilt der freigegebene [OAuth-Anwendungsablauf](/de/developer/oauth2).
- **Passwort:** `password/forgot` startet die Zurücksetzung und antwortet absichtlich gleich, unabhängig davon, ob die E-Mail-Adresse zu einem Konto gehört. Eine erfolgreiche Antwort bestätigt weder ein Konto noch die Zustellung der Nachricht. Falls CAPTCHA aktiviert ist, kann zusätzlich `cf-turnstile-response` verlangt werden. `password/reset/token` nimmt den Zurücksetzungstoken als Bearer-Token und ein neues Passwort im Feld `password` entgegen und **ändert das Passwort**; der Aufruf dient nicht nur der Tokenprüfung. `password/reset` ändert das Passwort einer angemeldeten Person mit `currentPassword` und `newPassword`. Prüfen Sie die tatsächliche Freigabe und Tokenlaufzeit in Ihrer Workspace-Version.
- **Sitzung:** `refresh/token` erneuert ein abgelaufenes Access Token mit einem gültigen Refresh Token. `logout/manual` beendet die Sitzung. Nach Logout darf ein zurückgezogenes Token nicht weiter verwendet werden.
- **SAML:** `GET /saml/signIn` beginnt die Weiterleitung zum Identitätsanbieter; der Callback verarbeitet dessen Antwort. `POST /saml/updateAppConfig` ist ein administrativer Konfigurationsaufruf.
- **Organisation:** `GET /orgAuthConfig/authMethods` gibt geordnete Anmeldeschritte zurück. `POST /orgAuthConfig/updateAuthMethod` ändert sie nach den oben beschriebenen Regeln; `POST /orgAuthConfig/` legt die Konfiguration an. Diese Aufrufe erfordern einen berechtigten Administrationskontext.

## Sicherheit und Fehlerbehebung

Die Referenz beschreibt gehashte Passwörter, begrenzte Lebensdauer von Anmeldesitzungen, signierte Tokens sowie Schutz gegen wiederholte fehlgeschlagene Anmeldeversuche. Ein fehlender oder abgelaufener Sitzungs-Token, eine nicht erlaubte Methode oder ein zusätzlicher Faktor kann den Ablauf unterbrechen. Prüfen Sie bei Fehlern die für den Workspace aktivierte Methode, die verwendeten Header und den nächsten vom Dienst angeforderten Schritt.

Für eigene Integrationen bietet die [OAuth-Anwendungsanleitung](/de/developer/oauth2) den vorgesehenen Freigabeweg. Bei Problemen mit einer produktiven Anmeldung hilft [Novaplan Support](/de/contact-us).
